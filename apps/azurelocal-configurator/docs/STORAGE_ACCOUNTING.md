# Storage design accounting checkpoint

Reviewed 2026-09-11, Azure Local 2604 baseline. This documents implemented design calculations, not native runtime qualification. The full saved design and implementation plan remain authoritative.

## Implemented model and boundaries

- Project schema 4 adds explicit source accounting scope, outside commitments, allocation basis/timestamps/references, source growth/alert/overcommit policies, tier allocation and usage, existing resiliency, per-node LUN presentation, management placement and explicit workload storage inclusion. Schemas 1–3 migrate without interpreting old numbers or free text as new observations. The nested mirror-accelerated choice is rejected in older schema versions.
- Every pool and array has an independent budget. S2D capacity is capacity-device bytes; cache and boot devices do not add usable space. Array capacity means usable pool capacity after array protection. SAN CSV capacity consumes its LUN and is not added again to the array.
- Fixed commitments use the desired footprint. Thin commitments use allocated footprint with an explicit planned or operator-observed basis. Desired nominal capacity and usage remain separate. Whole-source observations subtract listed existing observed allocations before adding remaining outside commitments; planned new allocations are then added once. Manual outside commitments cannot be combined with whole-source scope.
- Source headroom subtracts repair/operating reserve, metadata, listed and outside commitments, and growth. Growth is the greater of source policy and summed row reserves. This avoids adding two overlapping growth policies. Data reduction earns no automatic capacity credit. Unknown layout or observation scope leaves headroom unresolved.
- Microsoft dual-parity factors cover 4–16 nodes and distinguish HDD capacity from all-flash. Nested mirror-accelerated parity requires two nodes and at least four parity capacity drives per node, with parity columns capped at seven. Mixed SSD/HDD parity uses HDD count only. Allocated mirror/parity logical amounts are weighted independently, rather than multiplying all allocations by the desired volume's average factor.
- Logical placement compares workload demand plus growth with CSV size. It does not add demand a second time to source commitments. Linked management reservations use the greater of management and linked workload demand. Explicit included-in-parent storage requires a sizing basis, a direct independent parent, matching placement and sufficient parent reservation. External hosting is excluded.
- Workload CSV count changes have an explicit preview with stable IDs, removal rows and affected references. Platform-role CSVs, other sources and lifecycle-not-required rows are retained. New rows are fixed, with source mappings left for the operator. Stale previews are rejected. Removing a design row preserves references for correction and never operates infrastructure.
- MPIO checks include dedicated port ownership, protocol-shaped identities, node/fabric/array mappings, duplicate tuples, independent port/fabric/controller domains and expected optimized observations. Presentation records hold per-node visibility, writable stable identity, observed size, sector size, timestamp and evidence reference. These remain operator observations.
- Storage paths are separate Azure resources referencing CSV directories. Canonical path checks reject traversal, reserved names, prefix confusion, duplicate ownership and placement on platform CSVs. API resource naming and narrower portal naming are distinguished. Subscription, resource group, region, cluster and custom location are explicit.
